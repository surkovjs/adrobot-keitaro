# Adrobot

Приложение для создания кампаний Keitaro и редактирования офферов в существующих потоках.

**Стек:** FastAPI, SQLAlchemy, Alembic, SQLite; React, TypeScript, Vite. FastAPI отдаёт API и собранный интерфейс, поэтому для обычного запуска нужен один сервер.

## Быстрый запуск

Требуются Python 3.12+ и Node.js 22.12+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.lock.txt
cp .env.example .env
alembic -c backend/alembic.ini upgrade head
cd frontend
npm ci
npm run build
cd ..
uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Открыть <http://127.0.0.1:8000>. Документация своего API: <http://127.0.0.1:8000/docs>.

Перед запуском укажите в `.env` адрес Keitaro и API-ключ (см. ниже). Не перезаписывайте существующий `.env`, если подключение уже настроено. Приложение работает только с реальным Keitaro; при недоступности API показывает ошибку.

## Подключение Keitaro

В `.env`:

```dotenv
DATABASE_URL=sqlite:///./adrobot.db
KEITARO_URL=https://your-tracker.example
KEITARO_API_KEY=your-api-key
KEITARO_TIMEOUT=30
LOG_LEVEL=INFO
```

Адрес указывается без `/admin/#!/...`. Клиент обращается к `/admin_api/v1/`, передавая ключ в заголовке `Api-Key`. Ключ доступен только Python-серверу. `.env`, базы, зависимости и результаты сборки исключены из Git и Docker build context. После изменения `.env` перезапустите сервер. Без API-ключа или с адресом-заглушкой обращения к трекеру возвращают 503. `/api/health` возвращает `configured` и адрес только для настроенного подключения; `configured` подтверждает наличие настроек, а не доступность сервера или действительность ключа.

Понадобятся права чтения кампаний, потоков, офферов, доменов, групп и источников; для записи — создания/обновления кампаний и потоков, а также архивирования незавершённой кампании. Справочник групп запрашивается с `type=campaigns`.

Группа и источник запоминаются в браузере после успешного создания кампании, отдельно для каждого адреса Keitaro. Сохранённый выбор используется, только если он по-прежнему доступен в справочнике. Иначе, как и для домена, автоматически выбирается единственный доступный вариант. Все три значения можно изменить в форме. Создание новых доменов, групп, источников и офферов не входит в приложение.

Приложение предназначено для локального запуска на `127.0.0.1`. Собственной системы пользователей нет. Перед размещением в общей сети требуется добавить авторизацию или закрыть доступ на уровне reverse proxy. Для разных экземпляров Keitaro используйте отдельные базы, чтобы не смешивать историю редактора.

## Разработка

Все команды ниже выполняются из корня репозитория. Серверные исходники, миграции, тесты и Python-зависимости находятся в `backend/`, интерфейс — в `frontend/`. Общий `.env` остаётся в корне; его загрузка не зависит от текущей папки. Относительный путь SQLite в `DATABASE_URL` отсчитывается от корня репозитория, поэтому запуск из `backend/` использует ту же базу.

Сервер:

```bash
source .venv/bin/activate
uvicorn app.main:app --app-dir backend --reload --reload-dir backend --host 127.0.0.1 --port 8000
```

Интерфейс в другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Открыть <http://127.0.0.1:5173>. Vite проксирует `/api` на `127.0.0.1:8000`; отдельная настройка CORS не нужна. Изменения интерфейса видны сразу. Если интерфейс отдаёт сам FastAPI, после изменений повторите `npm run build` и обновите страницу. После первой сборки перезапустите FastAPI, чтобы подключились статические assets.

## Адреса экранов

- `/campaigns` — список кампаний.
- `/campaigns/new` — создание кампании.
- `/campaigns/:id` — редактор выбранной кампании.

Переходы управляются React Router. Прямое открытие ссылки и перезагрузка сохраняют выбранный экран; редактор заново загружает кампанию по ID из URL. Кнопки «Назад» и «Вперёд» работают с историей браузера. При уходе с несохранёнными изменениями, включая «Назад», запрашивается подтверждение. Черновик при перезагрузке не сохраняется.

FastAPI отдаёт `index.html` для этих адресов; неизвестные API-запросы и отсутствующие assets по-прежнему возвращают 404.

## Создание кампании

Принятая интерпретация ТЗ: **одна страна** и поток `country / accept`, то есть посетители из указанной страны → Google. Список гео из макета и противоположный фильтр `reject` не реализованы: это требует отдельного подтверждения автора ТЗ.

Форма принимает название, **один** ISO 3166-1 alpha-2 код страны, оффер, домен, группу и источник. Пробелы вокруг названия и кода удаляются, код приводится к верхнему регистру.

Последовательность:

1. Проверить существование и доступность выбранных объектов.
2. Создать выключенную кампанию с ротацией `position`.
3. Создать обычный поток с фильтром `country / accept / [GEO]` и HTTP-редиректом на `https://google.com`.
4. Создать замыкающий поток `default`, без лендингов, с выбранным оффером и долей 100%.
5. Прочитать потоки обратно и проверить маршрут; только после этого включить кампанию.

При ошибке до включения или подтверждённом отказе включить незавершённая кампания переносится в архив. После потерянного ответа на включение сервер перечитывает состояние. Если результат неизвестен, кампания не архивируется автоматически. Ответ содержит её ID, alias и результат восстановления. Архив восстанавливаемый; окончательное удаление не используется. Keitaro требует уникальные названия, в том числе относительно архива.

## Редактор и проценты

- Загрузка потоков из Keitaro, поиск офферов по ID и названию.
- Добавление оффера, удаление из потока и возврат ранее удалённого.
- Изменение процента автоматически закрепляет долю. Замок рядом позволяет закрепить/открепить её без ввода.
- Свободные доли делятся поровну из остатка после закреплённых. Целочисленный остаток раздаётся по возрастанию ID оффера, поэтому сумма всегда ровно 100% и результат не зависит от порядка строк.
- Пример: закреплено 25%, два остальных получают 38% и 37%; после добавления третьего свободного — по 25%.
- «Поровну» снимает закрепления и делит весь трафик заново.
- Минимальная доля активного оффера — 1%. Нельзя удалить последний оффер, оставить активный оффер с 0%, повторить один оффер или закрепить доли, не оставляющие трафика остальным.
- Изменения остаются в React до нажатия «Сохранить в Keitaro». «Отменить» возвращает загруженное состояние. При уходе с несохранёнными изменениями показывается предупреждение.
- Сохранение выполняется отдельно для каждого потока. Сервер повторно проверяет доли, доступность офферов и принадлежность потока кампании; отправляет только поле `offers`, затем читает результат обратно.
- Удаление из потока не удаляет сам оффер Keitaro. Удалённые строки и закрепления хранятся в SQLAlchemy, поэтому возврат доступен после загрузки кампании заново. Несохранённый черновик после перезагрузки страницы теряется.
- Редактируются потоки со схемой `landings` (лендинги и офферы). Фильтры, лендинги, триггеры и прочие настройки не отправляются при редактировании; redirect-потоки доступны для просмотра. Выключенный поток можно редактировать: сохранение не включает его.

Проценты рассчитываются чистыми функциями в `frontend/src/features/edit-stream-offers/model/editor-reducer.ts`, действия редактора — через `useReducer`. SQLAlchemy не подменяет Keitaro: источник актуальной конфигурации — API трекера.

## Повторы, конфликты и ошибки

Для POST/PUT обязателен UUID в `Idempotency-Key`. Сервер сохраняет журнал операций. Повтор завершённого запроса с тем же ключом возвращает прежний результат, другой payload под тем же ключом отклоняется. Незавершённые/ошибочные операции не запускаются автоматически повторно. После ответа с `outcome: failed` интерфейс выдаёт новый ключ для следующего ручного нажатия «Сохранить»/«Создать». При сетевом сбое, `unknown` или отсутствии подтверждённого результата ключ сохраняется. HTTP-статус сам по себе не определяет безопасность повтора.

Перед сохранением сервер сравнивает SHA-256 ревизию загруженного потока с актуальной. Если поток изменился в Keitaro, возвращается 409; нужно загрузить его заново и повторить правки. Это оптимистическая проверка, а не транзакция на стороне Keitaro: внешний клиент всё ещё может изменить поток между проверкой и PUT.

При тайм-ауте результат записи может быть неизвестен. Сначала загрузите данные заново или проверьте кампанию в Keitaro. Если тайм-аут случился при создании кампании до получения её ID, автоматический откат невозможен; найдите кампанию по alias из ответа или по уникальному названию. Не повторяйте создание вслепую. Журнал `operations` хранит стадии и ID известных созданных кампаний.

## Миграции

```bash
alembic -c backend/alembic.ini upgrade head
alembic -c backend/alembic.ini current
```

Рабочая схема содержит `stream_memory` (возврат офферов и закрепления) и `operations` (журнал записей). Миграция `0002` удаляет устаревшую таблицу `demo_entities` вместе с демонстрационными данными; перед обновлением сохраните резервную копию базы, если они нужны. Кампании в Keitaro эта миграция не затрагивает.

Откат для пустой/тестовой базы: `alembic -c backend/alembic.ini downgrade base`. Он удаляет локальные таблицы и их данные; не затрагивает Keitaro. Перед миграциями рабочей базы сохраните её резервную копию.

## Восстановление операций и журналирование

`Journal` хранит последнюю контрольную точку и время её записи в существующем `operations.result`: проверка, создание кампании/потоков, контроль результата, включение, сохранение локального состояния или архивирование. Старая схема журнала совместима; миграция для этого рефакторинга не нужна.

`RemoteWrite` различает «не отправлено», «отказ», «результат неизвестен» и «подтверждено». Создание кампании описывается отдельными состояниями. Подтверждённо выключенную незавершённую кампанию можно архивировать; включённую или потенциально включённую — нельзя. Ошибка локальной фиксации после включения оставляет результат `unknown`, а не запускает удаление.

Короткие SQL-операции выполняются последовательно в thread pool, а не в event loop. Память редактора и успешный результат операции фиксируются одной транзакцией. БД создаётся лениво при первом обращении; импорт модулей не создаёт engine.

- Явные отказы Keitaro (например, 422) и ошибки установления соединения завершают запрос как `failed`, сохраняя причину. Потеря ответа после отправки, обрыв протокола, невалидный ответ записи, 408 и 5xx считаются неоднозначными: сервер сверяет состояние, а если подтвердить результат нельзя — возвращает `unknown`. Одинаковый HTTP-статус нашего API не означает одинаковую безопасность повтора.
- Alias кампании детерминированно выводится из `Idempotency-Key`. После потерянного ответа на создание сервер ищет кампанию по alias, не повторяя POST.
- Если запись офферов завершилась ошибкой транспорта, сервер читает поток обратно. Подтверждённый результат сохраняется вместе с закреплениями. Отличающийся или недоступный результат получает `outcome: unknown`; перед новым действием нужно загрузить поток заново.
- Незавершённый запрос без новых контрольных точек более 10 минут при повторном обращении переводится из `pending` в `unknown`. Он не запускается повторно: нужно сверить состояние с Keitaro. Это также покрывает остановку процесса во время запроса.
- Журнал операций намеренно не очищается автоматически: удаление ключей позволило бы повторить старую запись. Для длительной эксплуатации потребуется согласованная политика хранения и архивирования журнала.
- При неопределённом результате сохранения или конфликте в уведомлении редактора доступна кнопка «Загрузить заново». Она использует ту же загрузку и подтверждение отмены черновиков, что кнопка в шапке.
- Ошибки API имеют объект `detail` с `message` и дополнительным контекстом; ошибки валидации также содержат `errors`.
- HTTP-клиент общий для процесса и закрывается при остановке. Справочники кэшируются на 15 секунд, записи сбрасывают кэш. Поиск офферов в интерфейсе локальный.
- Методы/пути запросов, HTTP-статусы, ошибки и компенсации логируются без заголовков и payload. Логи приложения видны в stderr при обычном запуске Uvicorn; уровень задаётся `LOG_LEVEL` в `.env` (по умолчанию `INFO`). Повторная инициализация не дублирует обработчики.

## Проверки

```bash
pip install -r backend/requirements-dev.txt
ruff check backend
pytest -c backend/pytest.ini backend/tests -q
cd frontend
npm test
npm run build
```

Настройки Ruff находятся в `backend/ruff.toml`, версия закреплена в `requirements-dev.txt`, чтобы сортировка импортов была одинаковой при запуске из корня и из `backend/`.

Серверные тесты используют отдельную SQLite в памяти, `tests/fake_tracker.py` и `httpx.MockTransport` для HTTP-адаптера. Проверяют маршрутизацию, повторы, валидацию, конфликт ревизий, архивирование частично созданной кампании, восстановление удалённых строк и сохранение закреплений. Тесты TypeScript проверяют расчёт для 1–100 офферов и действия редактора.

Для ручного теста интерфейса с несколькими имитированными офферами:

```bash
PYTHONPATH=backend:backend/tests python backend/tests/browser_fixture.py
```

Откройте `http://127.0.0.1:18002/campaigns/101`. Это отдельный тестовый процесс с шестью фиктивными офферами и временной SQLite. Он использует настоящий интерфейс и backend, но обращения к реальному Keitaro запрещены. Рабочий `.env` и база не используются. Остановка — Ctrl+C; временная база удаляется. Пользовательского demo-режима в приложении нет.

Для явной проверки **с записью в реальный Keitaro**:

```bash
python backend/scripts/smoke_live.py
```

Скрипт требует настроенный API-ключ, существующие группу и источник `FORTESTS`, хотя бы один доступный домен и оффер. Он создаёт одну новую кампанию `test_surkov_integration_<suffix>`, проверяет оба потока, повторы, конфликт ревизий и сохранение долей. На время редактирования кампания выключается; в `finally` созданная кампания **архивируется**, что подтверждается контрольным чтением. Существующие кампании не редактируются. Каждый запуск создаёт новый тестовый объект. Скрипт проверяет работающее приложение на `http://127.0.0.1:8000` (другой адрес: `--base-url`). Результаты сохраняются в `output/live-api-test/recheck.json` (другой файл: `--report`). Если доступно несколько офферов, проверяются добавление, удаление, возврат и закреплённые доли; иначе это явно отмечается как ограничение.

## Docker

Если `.env` ещё нет, создайте его и заполните `KEITARO_URL` и `KEITARO_API_KEY`:

```bash
cp .env.example .env
```

Не перезаписывайте настроенный `.env`. Затем:

```bash
docker compose up --build
```

Открыть <http://127.0.0.1:8000>. Compose читает `.env`, применяет миграции и сохраняет SQLite в named volume. Сборка фронтенда выполняется внутри Docker. Остановка: `docker compose down`; volume сохраняется.

## Архив для передачи

Не архивируйте рабочую папку целиком: в ней находятся локальная база и `.env` с ключом. Подготовьте архив исходников:

```bash
python backend/scripts/package_source.py
```

Получится `output/adrobot-source.zip` с папкой `adrobot/` внутри. В неё входят `.env.example`, `.gitignore`, `.dockerignore`, исходники, миграции, тесты и lock-файлы. Базы, `.env`, `node_modules`, сборка, `tsconfig.tsbuildinfo`, кэши и `__MACOSX` исключаются независимо от состояния Git. Рабочая база не удаляется. Если обязательного файла нет, упаковка завершается ошибкой вместо создания неполного архива.

Скрипт экспортирует текущие файлы рабочей копии (включая новые, не игнорируемые Git), а не только последний коммит. GitHub-публикация выполняется отдельно.

### Организация фронтенда

Редактор потока собран из `stream-offer-table`, `stream-editor-actions` и `readonly-stream`; хук `use-stream-editor` управляет черновиком, состоянием сохранения и ключом запроса. Расчёт процентов остаётся в чистом редьюсере. Полный компонентный тест проверяет добавление, сохранение, удаление и возврат после нового монтирования.

Страницы в `pages/` собирают готовые бизнес-возможности, а не выбираются вручную в `app.tsx`. Каждая страница является элементом маршрута React Router; общий каркас рендерит её через `Outlet`.

`entities` содержит модель предметной области и её представления. `features` содержит пользовательские действия: создание кампании и редактирование офферов потока. Внутри используются `model/` для состояния и расчётов, `ui/` для компонентов. `shared` содержит элементы без привязки к конкретной бизнес-сущности.

Общие справочники загружаются один раз на уровне провайдера приложения; данные отдельной кампании принадлежат странице редактора. Хуки отменяют устаревшие запросы при переходах. Изменения офферов остаются внутри reducer соответствующей фичи.

Имена файлов и папок фронтенда — **kebab-case** (`campaign-editor-page.tsx`, `edit-stream-offers/`), имена React-компонентов внутри файлов — **PascalCase** (`CampaignEditorPage`). Тесты лежат рядом с проверяемой логикой.

### Стили фронтенда

Компонентные стили находятся в соседних файлах `*.module.css`: например, `campaign-table.tsx` и `campaign-table.module.css`. Импортированный объект `styles` используется в `className`; имена классов изолируются при сборке. Адаптивные правила и состояния компонента находятся в том же модуле.

В `app/global.css` остаются шрифт, базовые настройки документа, сброс и общие правила доступности. Общие стили кнопок, полей ввода, панелей, заголовков и сообщений находятся в небольших модулях `shared/ui/`. Для сочетания классов используется `shared/lib/class-names.ts`. Строковые глобальные UI-классы и `:global` в компонентных стилях не используются.

Имена CSS-модулей также следуют kebab-case: `stream-editor.module.css`, `create-campaign-form.module.css`.

Импорты между папками фронтенда используют алиас `@`, указывающий на `frontend/src`: например, `@/features/edit-stream-offers/ui/stream-editor`. Импорты соседних файлов и CSS-модуля компонента остаются относительными (`./share-input`, `./stream-editor.module.css`). Алиас настроен в Vite и TypeScript; Vitest использует ту же конфигурацию Vite.
